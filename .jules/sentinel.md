## 2026-09-19 - [Fix double-free via size_t overflow in buffer reallocation]
**Vulnerability:** A `size_t` exponential growth strategy `buf_size *= 2` starting from 256 completely bypassed an equality check `if (buf_size == UINT32_MAX)` because it jumped from `2147483648` directly to `4294967296`. On a 32-bit system, this overflows to `0`. A subsequent call to `realloc(*data_ptr, 0)` is equivalent to `free(*data_ptr)` and returns `NULL`. The code then jumps to an error-handling block which performs a second `free(*data_ptr)`, creating a critical double-free vulnerability that could be triggered by reading an overly large run data file.
**Learning:** Exact equality checks against maximum bound constants like `UINT32_MAX` are brittle when values grow multiplicatively or exponentially. They can be cleanly bypassed, and integer overflow combined with `realloc(ptr, 0)` behaves exactly like `free()`, making subsequent error-cleanup frees dangerous.
**Prevention:** Always use `>=` or `<=` for bounds checks rather than `==`. When exponentially growing a buffer towards a known limit, clamp the growth explicitly using a check like `if (size >= MAX / 2) size = MAX; else size *= 2;`.
